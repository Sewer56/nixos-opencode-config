### ADHD-aware comments and docs
Shape comments and docs for an ADHD reader.

Wording, code-documentation, error-documentation, and accuracy win conflicts.

- Open with the point or next action, not an intro; context follows.
- Use the fewest numbered steps, one action each.
- Mark resulting states only where intent is unclear, never trivial code.
- Use `Next:` or checkable `Done when:` only for useful procedural guidance.
- No automatic closers on references, API summaries or module comments.
- API docs put errors and returns last.
- Errors: condition, cause and fix.
- Use concrete units for non-trivial work.
- Stop when done; no outro.
- No em dashes; use colons or periods.
- Full-explain requests, destructive actions and real ambiguity override shape.
- Harness and accuracy rules override shape.
- In these exceptions, keep the lead and drop closers.
